## 2. Сроки хранения персональных данных

*Значения по умолчанию для профиля `russia`; настраиваются оператором через переменные окружения и регламенты.*

| Тип данных | Срок хранения | Основание / настройка |
|------------|---------------|------------------------|
| Учётные записи пользователей (ФИО, email, логин, хэш пароля) | До удаления аккаунта администратором или по запросу субъекта | ФЗ-152 ст. 21; регламент оператора |
| Зашифрованные медицинские файлы | **7 дней** (по умолчанию) | `TTL_DAYS` в конфигурации; согласуется с врачебной практикой |
| Метаданные файлов в БД (имя, MIME, patient_id, хэши) | Срок жизни файла + период аудита | Политика оператора |
| Аудит-логи (JSON построчно) | **1095 дней (3 года)** | Профиль `russia`, `AUDIT_3_YEARS` |
| Временные расшифрованные файлы | До завершения ответа / **не более 1 ч** | Автоочистка `CleanupManager` |
| Токены одноразовых ссылок (`file_links`) | До истечения TTL или после исчерпания лимита скачиваний | Настройки ссылки при создании |
| DICOM view-токены | **15 минут** (по умолчанию) | `DICOM_VIEW_TOKEN_TTL_SECONDS` |

**Автоматическая очистка:** планировщик `CleanupManager` (`app/core/cleanup.py`), фоновые задачи при старте приложения.

## 3. Право субъекта на удаление данных

### 3.1. Как подать запрос

Субъект ПДн (пациент или пользователь) направляет запрос оператору:

1. **Через администратора клиники** (рекомендуется) — [email / регистратура / портал пациента заказчика].
2. **Письменно** на юридический адрес оператора.
3. **Через уполномоченное лицо оператора** по ПДн — контакт из раздела 1.

*Прямой самообслуживаемый интерфейс «удалить все данные» для пациентов без учётной записи в SMDG может отсутствовать — обработка через оператора.*

### 3.2. Процедура (обязанность оператора)

1. **Регистрация запроса** — в течение 1 рабочего дня.
2. **Идентификация субъекта** — по правилам оператора (документ, код, 2FA сотрудника и т.д.).
3. **Удаление в SMDG** (выполняет администратор оператора или подрядчик по заявке оператора):
   - удаление файлов пользователя (`DELETE /api/delete-user-file`, админ-API);
   - удаление учётной записи (`DELETE /api/admin/users/{id}`);
   - очистка связанных `file_links`, временных файлов, записей DICOM view-токенов.
4. **Подтверждение субъекту** — в срок, установленный оператором (рекомендуется до 3 рабочих дней).
5. **Максимальный срок исполнения** — не более **30 дней** (ФЗ-152), если иное не следует из закона.

**Важно:** удаление необратимо. Оператор уведомляет субъекта о последствиях до выполнения.

## 4. Журнал передачи персональных данных третьим лицам

### 4.1. Базовая поставка SMDG

В конфигурации **по умолчанию** (профиль `russia`):
- файлы хранятся **локально** на сервере оператора (`S3_ENABLED=false`);
- трансграничная передача **не предусмотрена** штатной конфигурацией;
- аналитика и телеметрия **не** отправляют содержимое медфайлов третьим лицам.

### 4.2. Опциональные интеграции (настраивает оператор)

| Интеграция | Данные | Условие |
|------------|--------|---------|
| **Webhooks** (`file.uploaded`, `file.downloaded`, `file.deleted`) | Метаданные события (без файла), подпись HMAC-SHA256 | URL и секрет задаёт оператор; фиксируется в журнале передач |
| **S3 / MinIO** (не используется в профиле `russia` по умолчанию) | Зашифрованные объекты | Договор с провайдером ЦОД в РФ — на стороне оператора |
| **Будущие PACS / МИС** | По ТЗ интеграции | Отдельное согласование и запись в журнал |

**Журнал передач** (рекомендуемый формат оператора):

- дата и время;
- субъект ПДн (при наличии);
- получатель (система / организация);
- цель передачи;
- основание (согласие / договор / поручение);
- объём и категория данных.

Копии событий дублируются в **аудит-логах** SMDG (`audit_logs/`, экспорт CSV/Excel/PDF).

## 7. Технические и организационные меры (кратко)

*Детали для службы ИБ — в документе [ARCHITECTURE_FOR_IB.md](ARCHITECTURE_FOR_IB.md) и [ARCHITECTURE_FOR_IB.pdf](ARCHITECTURE_FOR_IB.pdf).*

| Мера | Реализация в SMDG (`russia`) |
|------|------------------------------|
| Разграничение доступа | JWT + роли; обязательная 2FA для всех пользователей |
| Шифрование at rest | age, ключи в `/app/keys/` (Docker Secrets) |
| Шифрование in transit | TLS 1.3, HSTS (продакшен) |
| Аудит | Middleware аудита, экспорт для admin |
| Очистка | TTL файлов, ссылок, временных расшифровок |
| Rate limiting | Redis / slowapi, защита от brute-force |

**Не заявляется в базовой поставке:** сертификат ФСТЭК на СЗИ, промышленная криптография ГОСТ (есть задел), аттестация ИСПДн — отдельный проект оператора.

## 8. Доступ подрядчика к системе

- Доступ предоставляется **только** на период работ по акту/заявке заказчика.
- Рекомендуется: отдельная учётная запись `contractor`, VPN или bastion, журналирование сессий.
- По завершении внедрения: смена паролей admin, отзыв учётки подрядчика, акт приёмки.
- Подрядчик **не** копирует медицинские данные на личные носители и **не** использует прод-данные для демонстраций без обезличивания.
