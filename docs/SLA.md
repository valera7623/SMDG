# Service Level Agreement (SLA) — SMDG

**Версия:** 1.0  
**Дата:** 2026-04-25  
**Действителен до:** 2026-12-31  

## 1. Общие положения

### 1.1. Цель документа

Настоящий SLA определяет обязательства по доступности и производительности сервиса SMDG (Secure Medical Data Gateway) между поставщиком сервиса и заказчиком (организацией). Документ дополняет коммерческий договор и применяется к средам, явно указанным в приложении к договору.

### 1.2. Стороны

| Роль | Описание |
|------|----------|
| **Провайдер** | Команда эксплуатации SMDG (SMDG Operations) |
| **Клиент** | Организации, использующие SMDG по соглашению/лицензии |

### 1.3. Область действия (in scope)

- REST API SMDG (аутентификация, загрузка, скачивание, списки, DICOM, webhooks, админ-API);
- веб-интерфейс (страницы, отдаваемые приложением);
- DICOM Viewer (как компонент SMDG, при включённой функции);
- непрерывность записи в журнал аудита (хранимость согласно политике ретенции);
- публичные health/metrics, если отнесены к договору.

**Вне scope** (отдельные соглашения): инфраструктура заказчика, каналы связи, сторонние PACS, облачные квоты вне зоны ответственности провайдера.

## 2. Уровни обслуживания (Service Levels)

### 2.1. Доступность (Availability)

Совокупная доступность измеряется по SLI **доли успешных HTTP-запросов (2xx) к публичному API SMDG** за отчётный период, за исключением случаев из раздела 3, либо по эквивалентной метрике, согласованной в приложении (например, по synthetic probes).

| Уровень | Доступность (год) | Макс. непокрытого простоя / год* | Макс. / месяц (оценка)** |
|---------|------------------|----------------------------------|--------------------------|
| **Целевой (SLO)** | **99.9%** | **8,76 ч** | **~43,8 мин** |
| **Минимальный (порог ремедиации)** | 99,5% | 43,8 ч | ~3,6 ч |
| **Расширенный (опциональный tier)** | 99,99% | 52,6 мин | ~4,4 мин |

\* Для 99,9%: максимальное **целевое** время недоступности, выраженное в часах за 365,25 дня.  
\*\* Месячные лимиты — ориентир (365/12); расчёты в биллинге/кредитах ведутся за календарный месяц.

### 2.2. Производительность (Performance)

Ориентиры (не всегда отдельные обязательства, если в договоре не выделен отдельный SLO; измеряются в Prometheus / APM, см. [SLI.md](./SLI.md)):

| Метрика | Целевое значение | Метод |
|---------|------------------|--------|
| **API p95 латентность** | &lt; 500 мс | `http_request_duration_seconds` / `smdg_api_latency_p90` |
| **API p99 латентность** | &lt; 1000 мс | То же |
| **Загрузка (upload, типичный сценарий)** | &lt; 5 с на **10 МБ** при штатной сети | Эндпоинт `POST /api/upload`, трассировка |
| **DICOM рендер кадра** | &lt; 3 с (типичный сценарий) | DICOM API, `dicom_render_duration_seconds` |
| **Список файлов** | &lt; 200 мс p95 | `GET /api/list` (при пагинации по умолчанию) |
| **Экспорт аудита** | &lt; 30 с на **1000** записей (пригодно для пакетов) | Админ-экспорт (см. API аудита) |

### 2.3. Доступность по функциям (ориентиры)

| Функция | Целевой аптайм (ориентир) | Комментарий |
|---------|---------------------------|-------------|
| Аутентификация / сессии | 99,99% | Критичный путь |
| Загрузка / скачивание файлов | 99,9% | Основной продукт |
| DICOM Viewer | 99,9% | Мед. визуализация |
| Экспорт аудита | 99,5% | Админ-функция |
| Webhook доставка | 99,0% | Best-effort, ретраи; зависит от endpoint клиента |

## 3. Исключения (Exclusions)

Следующие ситуации **не** засчитываются как нарушение целевой доступности (при условии документирования и, где требуется, уведомления):

### 3.1. Плановое обслуживание

- Окна согласуются заранее; типичные примеры: **еженедельно** 02:00–04:00 (MSK), **ежемесячно** 01:00–05:00 (первое воскресенье) — конкретные график и продолжительность фиксируются в приложении/календаре.
- Минимум **7 дней** уведомления по согласованным каналам (email, Telegram, status page).
- Плановое время **вычитается** из `Downtime` при расчёте SLA, если отмечено в тикетинге/статус-странице.

### 3.2. Форс-мажор

Стихийные бедствия, войны, теракты, решения уполномоченных органов, отключения на стороне Tier-1 провайдера, деградировавшие не по вине SMDG.

### 3.3. Действия и инфраструктура клиента

- Некорректная конфигурация (DNS, TLS, firewall, rate limit client-side);
- превышение API rate limits (HTTP 429);
- использование **устаревших** или неподдерживаемых клиентов API;
- внутренние сети/прокси заказчика, блокировки, MITM, антивирус с SSL inspection.

### 3.4. Внешние зависимости

- Провайдер DNS заказчика, ISP, корпоративный прокси;
- глобальные DDoS/BGP-инциденты (см. раздел 7);
- отказ S3-совместимого хранилища **только** если по договору оно **не** в зоне ответственности провайдера.

### 3.5. События безопасности

Заблокированные запросы WAF, инциденты с подтверждённой компрометацией — по регламенту поставщика, без влияния на SLA, если требуется остановка сервиса по решению CISO/инцидент-респонс.

## 4. Мониторинг и измерение

### 4.1. Каналы и инструменты

| Канал | Назначение |
|--------|------------|
| **Prometheus** + **Grafana** | Метрики, дашборды, SLI |
| **Blackbox / synthetic** | Проверки снаружи (период, например, 30 с) |
| **Логи** | JSON/структурированные; хранение по политике (ELK/Loki и т.д.) |
| **Status page** | Публичный статус (`/status`, при включении) |
| **Алертинг** | Alertmanager → PagerDuty/Telegram/email по severity |

```yaml
# Пример: источники (обобщённо)
Метрики:
  - HTTP: стандартные + smdg_* (см. app/core/slo_metrics.py)
  - Probes: blackbox
Логи:
  - access / application JSON
  - тикеты инцидентов
```

### 4.2. Расчёт доступности (упрощённо)

\[
\text{Availability} = \frac{\text{TotalTime} - \text{Downtime\_eligible}}{\text{TotalTime}} \times 100\%
\]

- **Downtime_eligible** — периоды, когда SMDG не удовлетворяет SLO, **и** не попадает под раздел 3.  
- Согласованный **источник истины**: внутренние `smdg_slo_*` + внешние probes, зафиксированные в отчёте.

### 4.3. Пример (иллюстративно)

- Период: 30 суток = 43 200 минут.  
- Плановый простой (исключение): 120 мин.  
- Внеплановый простой (учтённый): 15 мин.  

\[
\text{Availability} = \frac{43\,200 - 15}{43\,200} \times 100\% \approx 99,965\%
\]

(Фактическая методика согласуется в приложении к договору.)

## 5. Компенсации (Service credits)

### 5.1. Матрица (месячная доступность, проектный уровень)

| Фактическое значение (месяц) | Сервисный кредит* |
|------------------------------|-------------------|
| 99,0% – &lt; 99,5% | 10% от месячной подписки (fee) |
| 98,0% – &lt; 99,0% | 25% |
| &lt; 98,0% | 50% (макс. в таблице) |

\*Кредит **не** является штрафом/неустойкой; применяется к **следующему** счёту, если клиент в течение **30** дней направит обоснованный запрос. Максимальная кумулятивная скидка за месяц согласуется в договоре (часто cap **50%** fee).

### 5.2. Условия

- Инциденты должны соответствовать критериям раздела 4.  
- Не кумулируется с кредитами за другой SLA (например, support), если в договоре не сказано иначе.  
- Force majeure / исключения из разд. 3 **не** дают кредит.

## 7. Безопасность и DDoS

### 7.1. Меры (ориентиры)

- Ограничение частоты (rate limiting) на API;
- WAF/обратный прокси, фильтрация, списки;
- DDoS-защита на уровне облачного/edge провайдера (CloudFront, AWS Shield, Cloudflare и т.д.);
- Горизонтальное масштабирование и readiness gates.

### 7.2. DDoS и SLA

Продолжительные DDoS могут **не** учитываться в uptime по соглашению сторон, если ведение журнала инцидента подтверждает внешнюю природу. Цель **восстановить нормальную** работу: ориентир **≤ 2 ч** с момента классификации как DDoS (не юридическая гарантия).

## 8. Отчётность

### 8.1. Ежемесячные отчёты

- Доступность и ключевые SLI/ошибка бюджета;  
- инциденты P1–P2 (время, причина, root cause на уровне, допустимом для КП);  
- планы улучшений.  

### 8.2. Канал доступа

- Grafana (закрытая/публичная view по согласованию);  
- email-рассылка;  
- **GET** `/api/slo/report` (админ, JSON) в продукте;  
- скрипт `scripts/monthly_sla_report.py` для офлайн-отчёта.
